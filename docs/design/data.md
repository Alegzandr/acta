# Acta design: data mapping

Part of the Acta design system. [DESIGN.md](../../DESIGN.md) is the index: direction, principles, the never-list and the review checklist. Section numbers are shared across all parts.

## 11. Data: what every element shows

Nothing on screen is illustrative. Every value comes from the model of ADRs 0005 to 0008 (Project > Epic > Topic, statuses, current state, timeline entries, notes, knowledge entries and revisions, working folders) or is computed from it by a rule stated here.

### Data model requests

For the lead. Each is something the design wants and the ADRs do not yet give; the design works without them today, in the way stated.

1. **Read markers.** The unread dot (tree, tabs, topic table, knowledge rows) needs, per record, when this installation last showed it: a `last_seen_at` per topic and per knowledge entry, local and not exported. Without it the dot can only cover changes that arrive while the app is running. **Done in M7 (schema 3):** a `read_markers` table holds `last_seen_at` per topic and knowledge entry, local, never exported or imported, never part of a record's stamp. A record is unread when its last write is Claude Code's and is newer than its marker (or it has none); records present when the migration runs count as seen. A page on screen (the active tab of any page group) and a memory unfolded in place mark their record seen; nothing is written for a record without a dot. The dot shows on topic rows, on a folded epic or project holding an unread topic (a folded project also for unread knowledge), on the Knowledge row of a project with unread entries, on knowledge rows (left of the author mark) and on background page tabs (the close button takes its place on hover). The topic table's dot is not drawn yet.
2. **Session presence.** Done (2026-11-21): `acta mcp` keeps a row per session (opaque session id, project and focus, launch token of Acta's terminal, start, last activity, heartbeat, state, last tool name, one line of what the agent logged) in `presence.db`, encrypted with the database key, apart from the main database so heartbeats never reload the pages. Rows expire 90 s after the last heartbeat and are deleted a day later.
3. **Links between records.** Backlinks and a "mentioned in" list, taken from Obsidian, need stable references in text (for example a link form that carries the UUID) or a relation table; the short ids are per-installation aliases and cannot serve after an import. Left out of v1.
4. **Setup check as data.** The four checks of `acta setup --check` and the path of the `acta` command must be callable from the app as structured results, not parsed from CLI text.
5. **Export history.** "Last export: 12 days ago" needs the time of the last export recorded (in the database or the preferences file; it must survive an update).
6. **Folders not found, across projects.** A query over all folder records for the Settings list and for bulk repair; no schema change, but the existence check must run off the UI thread for the whole set.
7. **Preferences outside the database.** `preferences.json` (4.7) is new: plaintext, no user content, holding typed page references for tabs (record ids or fixed page keys) and record ids for tree expansion. The lead should confirm that ids in a plaintext file are acceptable under the rule on plaintext data in CLAUDE.md; if not, tabs and expansion move into the database and only theme and language stay in the file.
8. **Entry count per topic** for the topic table should come from one grouped query, not one per row, to hold the 50 ms page budget with 1,000 topics.
9. **`updated_by` on every record** (human or Claude Code), next to `updated_at`: the Updated property, the current-state meta line and the knowledge rows' author mark all show who made the last write, and the ADRs record an author only on entries and knowledge revisions.
10. **System events.** The timeline shows status changes, creation and moves with their actor and time ("Alexandre set status to Active"). They need an event record per topic (kind, actor, time, old and new value), exported like entries.
11. **Trash metadata.** The trash page shows who deleted a record, when, and where it was, and restores it there: `deleted_at`, `deleted_by` and the original parent and position on every soft-deleted record.
12. **Revision descriptions.** The history list says what each revision did ("Replaced section Storage", "Edited", "Created from file"): a change kind, and the section where there is one, stored with each knowledge revision.
13. **Palette recents.** The last topics opened, per installation: record ids only, so they may live in the preferences file under the same condition as tabs (request 7).
14. **Project description.** Project pages show a description; ADR 0005's `update` takes topic, epic and note ids only. The project needs the field, and the tool or the UI needs to be able to write it.
15. **Drafts in the database.** Unsaved editor text survives navigation and restarts (6.4). It is user content, so it is stored in the encrypted database, keyed by record and field, local and not exported; never in `preferences.json`.

16. **Due dates** (the user's requirement of 2026-11-21: a due date on a topic, an epic or a project).
    - **Model.** One optional field per project, epic and topic: `due_on`, a calendar day stored as text `YYYY-MM-DD`, no time and no time zone (10.2.1). Years 2000 to 2099. No recurrence, no reminder, no notification: Acta shows a date, it does not chase anyone. No time of day, by decision: a plan needs the day; a time adds a time zone to every reading, a second field to every write, and a class of off-by-one bugs, and deadlines with an hour belong in a calendar.
    - **Store.** Additive migration, the next schema version after those already queued (ADR 0011's V3): a nullable `due_on TEXT` column on `projects`, `epics` and `topics`, with a check constraint on the shape; no backfill; a partial index on `(project_id, due_on) WHERE due_on IS NOT NULL` for the filters and `find`. Writes go through one domain function, `set_due(record, Option<Date>)`, that also records the system event (request 10: kind `due`, old and new value) and the `updated_at` / `updated_by` of request 9. "Overdue" and "open" are computed by one pure function, `due_state(due_on, today, open) -> None | Overdue(days) | Today | Soon(days) | Later(days)`, shared by the UI and the agent output so both always agree; `today` is passed in, never read inside, so it is testable.
    - **Export.** `due_on` on project, epic and topic objects, the ISO string or absent; the export format version goes up by one with a schema note and a test for the previous version (ADR 0006); older files import with no dates; import merges per record as today.
    - **Agent** (amends ADR 0005; output stays English and compact; "today" is the local date of the `acta` process):
      - `brief` of a topic adds one segment to its header line, only when there is a date: `· due 11-27 (6d)`, `· due today`, `· due tomorrow`, `· overdue 3d (due 11-18)`; a date in another year is written `2027-02-03`; a closed topic shows `· due 11-18` and is never called overdue. `brief` of an epic gives the epic's own segment on its header and the same segment, shortened to `· due 11-27` / `· overdue 3d`, on the line of each open topic that has a date. The project overview's overdue records are listed in the `Attention:` line of request 17, which replaced the `Overdue: ...` line first specified here. The session-start briefing is the `brief` text, so it carries the same segments within its 1,200 chars. Cost: at most 30 chars per line; the 300-token budget of `brief` is unchanged and enforced by the existing renderer.
      - `update` takes `due?`: `"YYYY-MM-DD"` sets, `""` clears. It accepts `P-n` as well as `T-n` and `E-n` for this field (projects have no other `update` field until request 14); on `N-n` it is refused. Ack: `ok T-42 · due 2026-12-15 (in 24d)` or `ok T-42 · due cleared`, so the agent sees the date it set. Natural language is refused, by design, so that the agent's writes are exact: `refused: due must be YYYY-MM-DD (2000-2099) or "" to clear, got "friday"`. Budget 40, unchanged.
      - `find` takes `due?: overdue | week`: open topics and epics whose own date is before today, or before today plus 7 (overdue included), combined with the other filters, ordered by date then by stored order; each line ends with its due segment. `limit=8`, budget 500, unchanged.
      - `create` items of kind topic or epic take `due?` with the same format, so a triage that sets dates is one call. Ack unchanged.
      - `tools/list` grows by about 250 chars of parameter descriptions; the existing test keeps it under 7,000. Budget tests add a seeded database where every record has a date and every topic is overdue.
    - **CLI.** `acta update T-42 --due 2026-12-15`, `--due ""` to clear; `acta find --due overdue|week`; `--json` carries `"due": "2026-12-15"` and `"overdue": true|false`.

17. **Overview** (the user's requirement of 2026-11-21: a few reference points that say where a project stands and what to do next, without noise; components-records.md 5, Overview section; screens.md 8.20).
    - **Model.** Nothing new is stored. Every figure is computed from records that exist: topic statuses and `created_at`, timeline entries (kind, system event kind and new value, `created_at`), due dates (request 16), notes (`filed_at`, `created_at`), knowledge entries (kind, `updated_at`). One pure domain function, `overview(scope, today) -> Overview`, where `scope` is a project or an epic and `today` the local date passed in (as for `due_state`), returns the four attention counts with the inbox's oldest age, and, for a project, the Last 7 days counts, the epic rows and the stale-memory count. A second, `overview_list(scope, filter, today)`, returns the records behind each count; the counts are `len()` of the same filters, so a number and the list it opens cannot disagree. The UI and the agent call the same two functions.
    - **Definitions** (local days, 10.2.1; "since" is local midnight 6 days before today, so the window is today and the six days before it):
      - *Blocked*: topics not deleted, status Blocked.
      - *Overdue*: open topics with `due_state` Overdue. The agent line adds overdue epics, as `find(due=overdue)` does; the UI counts topics only, to equal the table filter it opens.
      - *No activity*: topics with status Active whose last activity, `max(entries.created_at)` over the topic's entries not deleted (every kind, system events included, so a status change or a new state counts), else the topic's `created_at`, falls on a local day at least 7 days before today. Edits to the description or title write no entry today and do not count; if they ever write a system event, they will.
      - *Inbox*: notes with `filed_at` null and not deleted; shown when the oldest `created_at` is at least 7 local days old.
      - *Done in the last 7 days*: topics whose status is Done now and that have a system event of kind status with new value done since then (a topic done and reopened in the window is not counted).
      - *Decided*: decision entries not deleted created since then; the list is their distinct topics.
      - *Created*: topics not deleted with `created_at` since then.
      - *Memories not updated*: knowledge entries of kind memory, at every level of the project, not deleted, with `updated_at` on a local day at least 90 days before today.
      - Fixed thresholds (7, 7, 90 days), not settings: a setting would be one more thing to tune and explain, and the numbers are chosen so that a line appearing always means something.
    - **Store.** One additive index, in the next schema version after those queued (it can ride with request 16's): `CREATE INDEX entries_recent ON entries(created_at) WHERE deleted_at IS NULL AND (kind = 'decision' OR (kind = 'system' AND event = 'status'))`, so the Last 7 days counts read only the window's few rows instead of every entry. Everything else uses existing indexes: topics and due dates are in memory; last activity is one grouped `max(created_at)` over `entries_topic (topic_id, created_at)` for the Active topics only; the inbox is `count(*)` and `min(created_at)` over `notes_project`; memories use `kb_project`. No export change: nothing new is stored.
    - **Budget.** The whole `overview` of a project of 10,000 topics, 200,000 entries, 2,000 notes and 1,000 memories in at most 5 ms on the store thread, so the project page keeps its 50 ms open budget; recomputed after a model change on the same debounce as the page, never per frame. Tests: each definition on a seeded database, including the edges (an Active topic whose only activity is exactly 7 days old, a topic done then reopened in the window, a note dismissed, a deleted decision, a memory at 89 and 90 days, a daylight-saving change inside the window); `EXPLAIN QUERY PLAN` for each query names its index (a timing assertion would be flaky in CI; the timing is measured locally and reported).
    - **Agent** (amends ADR 0005 and the project overview line of request 16; English, compact, exceptions only):
      - `brief` of a project adds at most **one** line, and only when something needs attention, at most 160 chars, cut at item boundaries with `+N`: `Attention: blocked T-12, T-31 · overdue T-42 3d, E-3 2d +1 · idle T-7 12d, T-9 8d · inbox 6, oldest 12d`. Segments in the order of the UI, each present only when non-empty; the `inbox` segment only past 7 days, as in the UI. It **replaces** the `Overdue: ...` line of request 16, whose `due within 7 days: N` tail is dropped: it is not an exception, and `find(due=week)` answers it on request. It is written right after the header line, before the epic and topic lines, which are what gets cut when space is short.
      - `brief` of an epic adds the same line scoped to the epic, without the inbox, at most 120 chars.
      - `brief` of a topic adds one header segment only when the topic is Active and idle: `· no activity 12d`, so the agent that resumes it knows the state may be out of date and logs first.
      - Nothing of "More" (Last 7 days, epics, stale memories) is in agent output: none of it is an exception, and `find` and `kb` reach it when asked. No new tool and no new parameter, so `tools/list` does not grow.
      - The session-start briefing is the `brief` text, so it carries the line within its 1,200 chars. Cost: at most 160 chars on a project, 120 on an epic, 20 on a topic; the 300-token budget of `brief` is unchanged. Budget tests add a seeded database where every topic is blocked, overdue or idle and the inbox is old.


18. **Questions** (the user's requirement of 2026-11-21: questions to people outside the work, answered later, listed at every level; components-questions.md 5).
    - **Model.** A `questions` table: `id` (UUID), short id `Q-n` (ADR 0005, 0006), `project_id`, exactly one owner (`owner_kind` project | epic | topic, `owner_id`), `text` (1 to 300 chars), `asked_contact_id` (a contact of request 22, nullable; amended 2026-11-22, replacing `asked_to` and `asked_key`), `expected_on` (the `due_on` shape of request 16, nullable: the day the answer is expected), `status` open | answered | dropped, `answer` (Markdown, at most 1,500 chars, nullable; an answered question may have none), `resolved_at` and `resolved_by` (answered or dropped; human or Claude Code), `decision_entry_id` (nullable, the entry logged with the answer), `position` (stored order among the owner's questions), `created_at`, `created_by` (human or Claude Code), `updated_at`, `updated_by` (request 9), and soft delete with the metadata of request 11. Indexes on `(owner_kind, owner_id, status, position)`, `(project_id, status, expected_on)` and `(project_id, asked_key)`. Additive migration, the schema version after request 16's.
    - **Domain.** One function per change (`ask`, `edit_question`, `answer(question, text, log_decision)`, `drop_question`, `reopen_question`, `move_question`, `reorder_question`, `set_expected`), each writing `updated_*`. `answer` with `log_decision` creates the Decision entry (body: the question as a Markdown quote line, a blank line, the answer) in the same transaction and refuses when the owner is not a topic. Reopen clears `resolved_*` and keeps the answer text. Deleting or moving a topic, epic or project carries its questions (soft-deleted with the owner, restored with it). Questions write no system events (components-questions.md 5). A write to a question by another process marks its owner unread: request 1 grows to cover questions, so their rows get the dot too. "Overdue" is `due_state(expected_on, today, status == open)` of request 16.
    - **Export.** A `questions` array on each project, epic and topic object, every field above, references by UUID (the decision entry too); the format version goes up by one, shared with request 16 if both ship in one release; older files import with no questions.
    - **Agent** (amends ADR 0005; no new tool, as notes did: one more `kind`, not one more verb; output English and compact; every stored text, question, answer and person, inside the data fence like titles):
      - `create` items take `kind: "question"`: `title` (the question, max 300), `asked_to?` (max 80), `due?` (the answer date, `YYYY-MM-DD`, the exact refusals of request 16), `owner?` (`T-n`, `E-n` or `P-n`; default the focus topic, else the focus epic; with neither, the item is refused: `refused: pass owner (no focus)`). Ack: `ok Q-12 (T-42) · asked Marie · by 2026-12-04 (in 13d)`.
      - `update(id="Q-n")` takes `title?`, `asked_to?` (`""` clears), `due?`, `status?` (open, answered, dropped), `answer?` (max 1,500; with `status="answered"`, or alone to correct an answered question's answer), `log_decision?: bool` (only with `status="answered"`; refused on a question not owned by a topic: `refused: log_decision needs a question on a topic; Q-12 is on E-3`). Acks: `ok Q-12 answered · logged T-42#16 decision`, `ok Q-12 dropped`, `ok Q-12 reopened`. The agent cannot delete a question (human only, as everything else).
      - `find(kind="question")` lists the project's open questions by default; `status?` open | answered | dropped | all; combines with `query`, `epic`, `due` (`overdue` | `week`, on the answer date) and `person` (request 19). One line each, the text cut to 140 chars at a word: `Q-12 open T-42 · Marie · overdue 3d · Can we keep the v1 export format until March?`; answered: `Q-9 answered 11-19 T-42 · Legal team · Can the export leave the EU? -> Yes, inside the EEA only.` (answer cut to 100). Order: overdue first, then by answer date, then by owner and stored order. `limit=8`, budget 500, unchanged.
      - `brief` of a topic: after the state and before the entries, `Questions 3 open, 1 overdue:` (absent at 0), then up to 3 lines of the `find` form without `open` and the owner (`Q-12 Marie · overdue 3d · Can we keep…`), each at most 120 chars, chosen overdue first, then by answer date, then stored order. `brief` of an epic: the same count line and up to 2 lines for the epic's own questions, and ` · 2q` on the line of each topic with open questions. Project and epic: the `Attention:` line of request 17 gains one segment, after `overdue` as in the UI, `· answers late Q-4 3d, Q-9 1d +1` (open questions at every level of the scope whose answer date has passed), within that line's 160 / 120 chars; the Overview's `overview(scope, today)` adds the count to its attention set and `overview_list` the list behind it, so the line, the UI's fifth attention line and the Questions page's Overdue filter always agree. Over budget, the renderer drops the oldest entries first, then question lines from the last; the state and the count line always stay. The session-start briefing is the `brief` text, so it carries them within its 1,200 chars.
      - `instructions` gains one sentence and stays under 800 (607 today): "Record what only someone else can answer with `create` (kind question), and the answers with `update`."
      - Tests: budget tests on a seeded database where every topic has 50 open, overdue questions of 300 chars asked to 80-char names; `tools/list` under 7,000 chars; the stdio end-to-end test asks, finds, answers with `log_decision` and reads the entry back.
    - **Skill** (`using-acta`, a section "Questions for others", under 12 lines): record a question when the answer must come from a person or a place outside this session (a colleague, a client, another team, an office, a document you cannot reach) and the work should not guess: requirements, policy, money, access, other people's systems, anything hard to undo. Decide yourself, and `log` a decision, when the choice is technical, reversible and inside the task. When the user is the one who knows, ask them in the conversation instead. Search first (`find(kind="question", query=...)`). One question per item, answerable without context, at most 300 chars. Set `asked_to` only to a person the user named or Acta already lists, with Acta's spelling; never invent one. Set `due` only to a date the user gave. Say it in one line: "I added a question for Marie (Q-12)." Keep working on what does not depend on it; set the topic Blocked only when nothing else can move. When the user relays an answer, record it with `update(status="answered", answer=...)`, and `log_decision=true` when it settles a choice.
    - **CLI.** Flags carry only ids, dates, statuses and booleans; the question, the answer and the person are user text and come from stdin as one JSON object with the tool's field names (`{"title": "...", "asked_to": "Marie"}`), never from arguments (CLAUDE.md). `acta create question --owner T-42 --due 2026-12-04`, `acta update Q-12 --status answered --log-decision`, `acta find --kind question`; `--json` output carries every field.
