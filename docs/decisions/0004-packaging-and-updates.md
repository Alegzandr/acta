# 0004 - Packaging, silent install and auto-update

Status: accepted (macOS and Linux paths to be proven by the M1 releases)
Date: 2026-11-20

## Context
- Requirements: silent per-user install (no wizard, no admin), update at launch without asking, from GitHub Releases of the public repo `Alegzandr/acta`; CI on every push; a `v*` tag publishes everything. Zero budget, permanently: builds are unsigned and no tool may need a paid certificate or account.
- One codebase is the GUI, the CLI (`acta ...`, called from terminals and Claude Code hooks) and the MCP stdio server (`acta mcp`, alive for hours under a Claude Code session).
- Candidates, checked 2026-11-20:
  - Velopack 1.2.161 (2026-09-29; 1.3.39 is a prerelease), MIT, crate `velopack` + `vpk` CLI (a .NET tool, needs .NET SDK >= 8 to install). Windows `Setup.exe` (one click, per-user, `%LocalAppData%\{packId}`), macOS `.app` in a portable zip and a `.pkg`, Linux self-updating AppImage, delta packages, GitHub source built in. https://docs.velopack.io https://github.com/velopack/velopack
  - cargo-dist 0.34.0 + axoupdater 0.10.3: CLI-oriented (shell/PowerShell installers, MSI); no app bundle, AppImage, shortcuts or deltas. https://axodotdev.github.io/cargo-dist/book/
  - `self_update` 1.3.3: swaps a single executable; no installer, bundle or deltas.
  - cargo-packager 0.11.8 (2025-11-27) + cargo-packager-updater 0.2.3 (2025-07-21): NSIS/app/AppImage, but updates need a minisign key pair kept as a CI secret, run the full installer, have no deltas, and there has been no release for a year. https://docs.rs/crate/cargo-packager-updater/latest
- Facts read in the Velopack 1.2.161 source that shape the design:
  - Windows: `Update.exe` kills every process whose image is under the install root (`force_stop_package(&root_path)` in `src/bins/src/commands/apply_windows_impl.rs`), then renames `current\`. An `acta mcp` running from there dies on every update.
  - macOS and Linux: the bundle is swapped atomically (`renamex_np`) or the AppImage replaced with `mv`; nothing is killed.
  - `vpk pack` on macOS only warns when no signing identity is given; macOS packages can only be built on macOS; Windows and Linux packages can be built on their own runners. https://docs.velopack.io/packaging/cross-compiling
  - vpk copies `UpdateMac` into the bundle after staging, which invalidates a signature made before `vpk pack`.
  - `vpk upload github` does not upload `assets.<ch>.json` or `RELEASES-<ch>`, and writes each `releases.<ch>.json` feed anew from this version's full and delta packages (see Evidence, v0.1.2).
  - vpk 1.2.161 is a framework-dependent `net10.0` tool: its launcher needs a .NET 10 runtime under `DOTNET_ROOT` or in the system default location.
  - The bundled AppImage runtime is the static `type2-runtime`, so `libfuse2` is not required. Velopack reports every macOS and Linux install as portable.
- macOS 26 (tested by eclecticlight.co on 26.6.1, 2026-08-11): fully unsigned code never runs on Apple silicon; an ad-hoc signed app opens with no warning when it has no quarantine attribute and is blocked when it has one. https://eclecticlight.co/2026/08/11/how-can-you-run-code-that-hasnt-been-notarised/
- GitHub refuses to create or edit a release whose target commit differs from the default branch under `.github/workflows/` unless the token may write workflows, which `GITHUB_TOKEN` never may (see Evidence, v0.1.1).

## Decision
**Tooling.** Velopack, pinned: crate `velopack = "=1.2.161"`, `dotnet tool install -g vpk --version 1.2.161` (crate and tool versions must match). Pack id `Acta`, bundle id `io.github.alegzandr.acta` (a domain the project controls). One channel per target so asset names never collide in a release: `win-x64`, `osx-arm64`, `osx-x64`, `linux-x64` (later `win-arm64`, `linux-arm64`).

**Binary layout: two thin executables, one package, one version.**
- `Acta[.exe]`: GUI, `windows_subsystem = "windows"`, Velopack `--mainExe`; the only process that installs, updates or uninstalls anything.
- `acta-cli[.exe]`: console subsystem, CLI and `acta mcp`, same workspace and domain crates, no GPUI linked. It is named `acta-cli` inside the package because Windows and macOS file systems are case-insensitive.
- The GUI exports the CLI to a stable per-user directory outside the Velopack root, in the after-install and after-update hooks and again at every start (idempotent, compares a version marker). The export has a root of its own on every system, because that root is what an uninstall or a cleanup removes and it must never contain the data directory (`acta_core::paths`):
  - Windows `%LOCALAPPDATA%\ActaCli\bin\acta.exe`, added to `HKCU\Environment\Path` in the Velopack install hook (value type preserved, `WM_SETTINGCHANGE` broadcast).
  - macOS `~/Library/Application Support/ActaCli/bin/acta`, Linux `$XDG_DATA_HOME/acta-cli/bin/acta` (default `~/.local/share/acta-cli`). `~/.local/bin/acta` is a symlink to it, created at first start and only replaced when it already points into Acta's export root, so a foreign `acta` there is left alone. `acta setup` adds `~/.local/bin` to the shell profile when it is missing; the install scripts change no PATH.
  - Replacement is rename-aside then copy then rename: a running `acta.exe` cannot be overwritten on Windows but can be renamed. Old files are deleted on a later start once unlocked.
- Data: `%LOCALAPPDATA%\ActaData`, `~/Library/Application Support/Acta/data`, `$XDG_DATA_HOME/acta/data`. Log: `%LOCALAPPDATA%\ActaData\logs\acta.log`, `~/Library/Logs/Acta/acta.log`, `$XDG_STATE_HOME/acta/acta.log` (default `~/.local/state/acta`).
- Claude Code configuration (MCP command, hooks) always references the exported path, never `current\`.

**Update policy.**
- Only the GUI updates. At launch it checks the feed and, if an update exists, downloads (delta first), applies and relaunches before the main window opens. Budgets: 2 s for the feed check, 5 s for the download, then 1 s for the worker to hand the apply to the UI thread, which writes the preferences and applies (Velopack ends the process there; a failed apply opens the window as it is). An ordinary installed launch may therefore wait up to about 7 s before the window. `GithubSource` exposes no network timeout, so the budgets are enforced around it. If the check or download is slow or fails, the app opens normally, the download continues in the background and Velopack applies it at the next launch. No prompt in either case.
- A launch started by the updater never applies an update, which prevents a relaunch loop after a failed apply; it opens immediately. The portable flag is honoured on Windows only.
- The CLI and MCP server never update themselves and never run from the Velopack root. A running MCP server keeps its old version until its Claude Code session restarts; every new `acta` invocation gets the new version.
- Compatibility rule that makes this safe: the database written by version N+1 must stay usable by version N. Migrations between adjacent releases are additive only; a destructive change is split over two releases. Each process checks the schema version when it opens the database and, if it is too old to continue, the CLI/MCP answers with one short "restart the session to load Acta x.y.z" error instead of writing.
- Update source: since 0.1.4, `https://github.com/Alegzandr/acta/releases/latest/download/` (`update_source.rs`). The feed `releases.<channel>.json` is fetched there with no query string and a 10 s timeout. Its delta packages are dropped, so clients always download the full package. Packages are fetched through `HttpSource` on the same base, with a 15 min timeout per package, and only if the feed names a bare file name. The launch budgets are unchanged. These are plain downloads that GitHub redirects to the latest published, non-pre-release release, so no API rate limit applies. Drafts and pre-releases are never latest, so marking a release as pre-release still hides it from clients (yanking, `docs/releasing.md`). Up to 0.1.3, apps used `GithubSource` without a token: the REST API, at 60 requests an hour per IP, shared by everyone behind that address.
- Uninstall: the hook exists on Windows only. It removes the PATH entry, terminates processes running from the exported directory, deletes it, and deliberately leaves `%LOCALAPPDATA%\ActaData`. macOS and Linux have no uninstall hook; `docs/install.md` lists what to delete by hand. The data directory is never removed by anything Acta ships.

**Installation, unsigned, free means only.**
- Windows: `Acta-win-x64-Setup.exe`, plus a documented one-liner `irm <release>/install.ps1 | iex` that downloads and runs it with `--silent`.
- macOS: recommended path is `curl -fsSL <release>/install.sh | sh`: it downloads the portable zip with curl (no quarantine attribute), unpacks `Acta.app` into `~/Applications` and opens it. The bundle is signed ad hoc inside `vpk pack` (`--signAppIdentity -`; vpk then runs `codesign -s - -f --timestamp --options runtime --entitlements <its default> --deep`), and `scripts/package.sh` fails the build unless the bundle inside the portable zip verifies. The `.pkg` is not shipped (`--noInst`): unsigned it only adds a second warning.
- Linux: the same `install.sh` puts the AppImage in `~/.local/share/acta/`, marks it executable and starts it. vpk builds the AppImage with `mksquashfs` (`squashfs-tools` on the runner). At the first start of an installed AppImage the GUI writes `$XDG_DATA_HOME/applications/acta.desktop` and `$XDG_DATA_HOME/icons/hicolor/512x512/apps/acta.png`.
- Every release carries `SHA256SUMS` and a GitHub build provenance attestation (free on public repos; `gh attestation verify`). Velopack checks the SHA-256 from the feed before applying.
- Assets per release: `Acta-win-x64-Setup.exe`, `Acta-win-x64-Portable.zip`, `Acta-osx-arm64-Portable.zip`, `Acta-osx-x64-Portable.zip`, `Acta-linux-x64.AppImage`, and per channel `Acta-<v>-<ch>-full.nupkg`, `Acta-<v>-<ch>-delta.nupkg`, `releases.<ch>.json`; plus `SHA256SUMS`, `install.sh`, `install.ps1`. `assets.<ch>.json` and `RELEASES-<ch>` stay build-side.
- Third-party notices ship in every package, in a `licenses` directory (next to the executables on Windows and Linux, in `Contents/Resources` on macOS), collected by `scripts/licenses.sh`: `THIRD-PARTY-RUST.txt` for the whole Rust dependency tree, every licence file found under `assets/` (by name, so a change of fonts needs no change here; a font directory without one fails), and the files of `scripts/licenses/third-party` (Lucide's licence: the icons are copies, in `assets/icons/lucide`, of the SVGs bundled in the `gpui-kit-assets` crate, whose own licence does not carry Lucide's; that directory holds no licence file of its own). The Rust part is generated at build time by cargo-about 0.9.3 (MIT/Apache-2.0, free), not checked in: a checked-in file needs the same tool in CI to prove it is current and adds a 590 kB diff to every dependency bump, while generating costs a few seconds with the release binary, which `scripts/ci/install-cargo-about.sh` installs after checking a pinned SHA-256. `about.toml` lists the accepted licences, so a dependency with any other licence fails CI (Linux job) and the release `check` job. The packaging scripts refuse to run without the directory.

**Actions and credentials (all workflows).** Actions are pinned to full commit SHAs with the release in a trailing comment: a tag of an action can be moved to other code, a commit cannot, and these actions run with the release token. Resolved with `gh api repos/<owner>/<repo>/commits/<tag>` on 2026-11-20: `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1` (v7.0.1), `Swatinem/rust-cache@d1527c8f67ef9af357290475d4af4b0fab8f12e0` (v2.9.3), `actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9` (v7.0.2), `actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333` (v8.0.2), `actions/attest-build-provenance@4d101475d8b20a2381f78447822ac1eab6504dd8` (v4.2.2). Bumping one means resolving the new tag the same way and changing the SHA and the comment together; nothing updates them automatically. Every checkout uses `persist-credentials: false`. Every job that runs vpk derives `DOTNET_ROOT` from `dotnet --list-runtimes` (the install that owns a 10.x runtime), fails with a clear message if there is none, and starts vpk once before packaging; the packaging scripts also start vpk once themselves, because a vpk that cannot start was reported as "no previous release". `actions/setup-dotnet` is not used: the runtime is already on the runners, and the action would download an SDK in five jobs to set one variable. It becomes necessary the day an image drops .NET 10; the error message says so.

**CI workflow (`ci.yml`, every push and pull request).** `fmt` job on ubuntu (`cargo fmt --all --check`) that the others need; then matrix windows-latest, macos-latest, ubuntu-latest: `Swatinem/rust-cache`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`. Concurrency group cancels superseded runs. `permissions: contents: read`.

**Release workflow (`release.yml`).** Runs on a `v*` tag, and as a dry run (no release, no attestation, no job with write permissions) on pushes to `main` and on `workflow_dispatch`; the dry run is where a broken release build of any channel, including `osx-x64`, is caught before a tag. `permissions: contents: read` at the top; `GITHUB_TOKEN` only, no secrets. Procedure and repository settings: `docs/releasing.md`.
1. `check`: refuses a tag whose commit is not an ancestor of `origin/main`, before running anything from that commit, and fails unless the tag equals `v` + the workspace version from `cargo metadata` and the `velopack` crate in `Cargo.lock` has the version of the `vpk` the workflow installs. It generates the `licenses` directory once, for all targets; the build jobs take it as an artifact.
2. `build`, matrix: windows-latest (`win-x64`), macos-latest arm64 building both `aarch64-apple-darwin` and `x86_64-apple-darwin` (fallback `macos-26-intel`), ubuntu-22.04 (`linux-x64`, old glibc baseline). Steps: checkout, `cargo build --release --locked`, stage `Acta` + `acta-cli` (macOS: assemble `Acta.app`), `vpk download github --repoUrl ... --channel <ch>` (previous release, needed for the delta; tolerated to fail on the first release), `vpk pack --packId Acta --packVersion <v> --runtime <rid> --channel <ch> --mainExe Acta[.exe] --icon ...`, upload the output directory as an artifact. Tag builds restore no cargo cache: a cache entry can be written by any earlier run on `main`, and nothing such a run left behind may end up in a release; the cost is a full release build per channel on every tag. Dry runs read the cache and only `main` saves it.
3. `collect` (read-only, every run): gathers the four build artifacts, writes `SHA256SUMS` over the packages and the two install scripts, and hands it on with them as the `release-extras` artifact. It passes the SHA-256 of `SHA256SUMS` as a job output.
4. `publish` (`contents: write`, `id-token: write`, `attestations: write`): a job-level `if` makes it exist only for a `v*` tag push; it runs in the `release` environment and checks out no code. It compares the digest of `SHA256SUMS` with `collect`'s output before anything else, checks every listed file, attests, creates the draft itself with `gh release create "$TAG" --verify-tag --draft` and no target (with no target GitHub checks the default branch and the release stays on the existing tag; never `--target` or vpk's `--targetCommitish`), runs `vpk upload github --channel <ch> --merge --tag v<v> --releaseName "Acta <v>"` once per channel into it, and uploads the install scripts. It then checks that every asset GitHub serves has the `collect` digest and that each served feed lists exactly the channel's full and delta packages of this version, each entry matching the verified file's size, SHA-1 and SHA-256, with one full package per feed. It appends the feeds' hashes to `SHA256SUMS`, attests the feeds, uploads `SHA256SUMS` last, checks its digest, and publishes.

## Alternatives
- One `acta.exe` with the GUI subsystem and `AttachConsole(ATTACH_PARENT_PROCESS)`: the shell does not wait for a GUI-subsystem process, so the prompt returns first and output and interactive stdin are unreliable. Only redirected pipes work.
- One console-subsystem `acta.exe` that frees its console for the GUI: a console window flashes at every GUI launch; the manifest `consoleAllocationPolicy` that avoids it exists only on Windows 11 24H2 and later.
- Either single-exe variant also leaves the MCP server inside the directory Velopack kills and renames, so a second copy is needed anyway.
- cargo-dist + axoupdater, `self_update`: built for CLIs, no desktop integration. cargo-packager: paid nothing but needs a signing secret, runs a full installer per update, stale.
- Hand-rolled updater: full control, but we would own delta, rollback, shortcut and registry code on three OSes.
- `GithubSource` without a token (the choice up to 0.1.3): it reads the same latest feed, but through the REST API, whose unauthenticated quota is shared per IP. On 2026-11-21 the update check of 0.1.0 failed with "network error" at every launch on the macOS and Linux runners, while Windows updated (update-e2e run 44847527497). The objection to `releases/latest/download/` was that a feed entry could point at an asset of an older release. That does not happen: `vpk upload` writes each release's feed with that version's own full and delta packages only (v0.1.2 draft, four channels).
- Universal macOS binary: one artifact, twice the download on every update.
- Signing the bundle before `vpk pack`: vpk's copy of `UpdateMac` invalidates it.
- A GitHub App token with Workflows write so the draft can carry a target commit: works, but adds a long-lived secret.

## Consequences
- What users see, permanently:
  - Windows: a `Setup.exe` downloaded with a browser shows SmartScreen "Windows protected your PC"; "More info" then "Run anyway". With Smart App Control on, unsigned executables are blocked with no per-app override; the user has to turn it off. Antivirus false positives are possible. Updates are fetched by `Update.exe` itself and showed no prompt in the spike.
  - macOS: with `install.sh` no warning is expected. A zip downloaded with a browser is quarantined and Gatekeeper blocks it; the user must use System Settings > Privacy & Security > "Open Anyway", or run `xattr -dr com.apple.quarantine`. Self-update is expected to keep working unsigned because Velopack downloads without quarantine and the new bundle is ad-hoc signed; this is unproven until the M1 release.
  - Linux: no warning. A manually downloaded AppImage needs `chmod +x`.
- An ad-hoc signature has a new identity on every build, so macOS keychain items bound to the app's signature will prompt again after each update. ADR 0003 must take this into account.
- Without signing, update integrity rests on HTTPS to GitHub plus the feed checksum: whoever controls the GitHub account controls every install. Protect the account (2FA) and the tag.
- Splitting `collect` from `publish` protects the token, not the bytes: `publish` uploads whatever the build jobs produced and `collect` hashed, so those jobs, the code of the tagged commit and the runners are trusted for the content of a release. The checks in `publish` only establish continuity, and the provenance attestation says which workflow run built the files, not that the run was honest.
- The ancestor check catches a tag put on the wrong commit; it cannot stop someone who can push a tag, because the workflow that runs is the one in the tagged commit. The barriers for that are repository settings, applied by the owner (`docs/releasing.md`): a tag ruleset on `v*` (no update, no deletion, no force push), immutable releases, and the `release` environment restricted to `v*` tags. All three are free on a public repository.
- The two-executable layout departs from "the same binary"; what is kept is one install, one version, always in sync.
- A CLI process still running at uninstall keeps its file locked; the uninstall hook must terminate it (the spike left one file behind without that).
- Velopack writes `%LocalAppData%\velopack\velopack_<id>.log`, which uninstall does not remove.
- CI depends on the .NET runtime preinstalled on GitHub runners.
- Revisit if Velopack 1.3 becomes stable (pin both sides together), if GitHub changes the `releases/latest/download/` redirect, or if a free signing route appears.
- To verify in M1 on real runners and a real release, because it cannot be done locally: `vpk pack` unsigned on macOS and the ad-hoc signature through packaging; first launch and self-update on macOS arm64 and x64; AppImage install, desktop entry and self-update; the update source against real release assets (`GithubSource` until 0.1.3, `releases/latest/download/` from 0.1.4); `vpk upload --merge` from one job for four channels; both `install` scripts; SmartScreen on a browser download. The checklist is in `docs/releasing.md`.

## Evidence
Spike: `spikes/updater` (Windows 11 26300, rustc 1.97.1 MSVC, velopack 1.2.161, vpk 1.2.161, .NET SDK 10.0.302). `pack.ps1 <version>` builds and packages; the feed was the `releases/` folder served on `http://127.0.0.1:8765/` through `HttpSource`. Observed on Windows only:
- `vpk pack` took under 1 s and produced `ActaSpike-0.0.1-win-x64-full.nupkg`, `ActaSpike-win-x64-Setup.exe` (11.6 MB for a 3.4 MB app), `ActaSpike-win-x64-Portable.zip`, `releases.win-x64.json`; packing 0.0.2 in the same folder added a 2.9 kB delta. Without `--runtime` vpk assumes x86.
- `Setup.exe --silent` from a non-elevated shell: exit 0 in 2.1 s, no elevation, app not launched (without `--silent` it launches). Created `%LocalAppData%\ActaSpike\{current\, packages\, Update.exe, Acta Spike.exe stub}`, Start menu and Desktop shortcuts targeting `current\Acta.exe`, and `HKCU\...\Uninstall\ActaSpike` (with `QuietUninstallString`); nothing in HKLM. The after-install hook exported `acta.exe` and added its directory to the user PATH.
- Self-update: launching the installed 0.0.1 fetched the feed and the delta, applied it and relaunched as 0.0.2 about 1.0 s after start. `DisplayVersion` became 0.0.2 and the exported CLI reported 0.0.2. With the feed unreachable the check failed after 2.0 s and the app carried on.
- Processes alive during the update: `current\acta-cli.exe mcp` and a second `current\Acta.exe` were killed by `Update.exe` (logged "Killing process"). `ActaSpikeCli\bin\acta.exe mcp`, outside the root, kept running as 0.0.1; its file was renamed aside and the new CLI installed next to it.
- `Update.exe --uninstall --silent`: root directory, shortcuts and registry key removed, user PATH byte-identical to the backup. Failure: the exported directory was not deleted (access denied) because the surviving MCP process still held the renamed file; it was removed once that process ended.
- A GUI-subsystem exe writes to a redirected pipe correctly; interactive console behaviour was not tested.
- Not tested: macOS, Linux, GitHub as the source, a browser-downloaded installer, Smart App Control.

From the M1 pipeline:
- First dry run: on the macOS runners (image `macos-26-arm64` 20261117, SDKs 8 to 11 preinstalled) .NET lives outside the default location and no `DOTNET_ROOT` is set, so `dotnet tool install` succeeded and vpk then failed with "You must install .NET to run this application". The Windows and Ubuntu runners worked as they are.
- v0.1.1 (2026-11-20) built but did not publish: `vpk upload github --targetCommitish $GITHUB_SHA` got 403 "Resource not accessible by integration" when it created the draft. v0.1.0 passed because `main` was still at the tagged commit; for v0.1.1, `main` had taken a change to `update-e2e.yml` (600dbe3, 23:38) before `publish` ran (23:47). The REST docs for creating and updating a release state the workflow-write rule above. No settings were relaxed and no extra token was added. v0.1.1 stays a tag without a release (the ruleset keeps it).
- v0.1.2 (2026-11-21) stayed a draft on the workflow's own check: its `releases.<channel>.json` feeds differed from the hashed ones. With a previous release, `vpk pack --fetch-previous` writes a feed that also lists the previous full package (`Acta-0.1.0-<ch>-full.nupkg`); `vpk upload github` (1.2.161) does not upload that file and writes the feed anew from this version's full and delta only. This held on all four channels. Every package and install script in the draft had exactly the digest `collect` computed. The v0.1.2 draft is not published; the next release is v0.1.3.
- Deltas: the latest feed holds the latest full package and only the delta from the release before it. `GithubSource` merges the feeds of the ten most recent releases, so it offers a delta chain. Velopack 1.2.161 (`create_delta_update_strategy`) applies every delta newer than the installed version to the installed package. It checks neither the delta's base nor the patched result: the `.shasum` check in `Update patch` is commented out, and only zstd's frame checksum on changed files remains. A client further behind than one release would rely on that alone. `LatestRelease` therefore drops the deltas, and every update downloads the full package (12.5 to 22 MB per channel for 0.1.2), which Velopack checks against the feed's SHA-256 and size before applying. Trade-off: bigger downloads, always a correct base. Serving deltas again would need a feed that holds a correct chain, or a check of the delta's base.
- 2026-11-21, after v0.4.0: applying an update showed Velopack's own native progress dialog (Update.exe without `--silent`, from `apply_updates_and_restart` and from `VelopackApp`'s startup apply). Every apply now runs the updater with `--silent` (`wait_exit_then_apply_updates(asset, true, true, [])`, then exit), Velopack's startup apply is off, and a package left on disk by an earlier launch is applied by Acta's own launch path, with Acta's updater window the only thing on screen. The guard against a relaunch loop (no apply in a launch the updater started) covers that path too.
